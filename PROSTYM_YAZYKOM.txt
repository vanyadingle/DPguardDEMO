2. ОТКУДА БЕРУТСЯ "РЕАЛЬНЫЕ" ДАННЫЕ?
================================================================================

Файл data/ue_sessions.json — это 12 записей абонентских сессий (UE).

Каждая запись похожа на строку из базы данных оператора:
  UE-003: slice eMBB-1, threat_score=55, auth_failures=3, anomaly=да

Из этих записей программа САМА считает агрегаты:
  - threat_level = 71 (максимальная угроза среди сессий)
  - active_connections = 8 (сколько сессий на slice eMBB-1)
  - failed_auth_attempts = 19 (сумма неудачных авторизаций)
  - и т.д.

Это "реальная телеметрия" в учебном смысле: структурированные записи,
как в настоящей 6G-сети, только не из live-сети, а из JSON-файла.

================================================================================
4. НОВЫЕ МОДУЛИ ПРОСТЫМИ СЛОВАМИ
================================================================================

network_telemetry.py — "Сборщик данных"
  Читает JSON с сессиями, считает KPI, между эпохами симулирует
  рост угроз (как будто атака развивается).

openai_planner.py — "Настоящий мозг" (если есть API-ключ)
  Отправляет запрос в ChatGPT/OpenAI.
  Получает JSON: какие метрики прочитать и что сделать.
  НЕ отправляет raw данные — только intent и схему.

mock_llm.py — "Мозг-заглушка" (без интернета/ключа)
  Заранее знает что ответить. Для демо в университете идеально.

privacy_policy.py — "Правила доступа"
  security_operator может block_traffic.
  readonly_auditor — только monitor_only.
  Каждая метрика имеет min/max epsilon.

action_executor.py — "Руки системы"
  Реально выполняет команды: block_traffic удаляет аномальные сессии
  из данных, rate_limit уменьшает трафик.

audit_log.py — "Чёрный ящик"
  Записывает всё в logs/audit.jsonl — можно показать преподавателю
  что система логирует каждое решение.


================================================================================
5. ЧТО ПРОИСХОДИТ В 3 ЭПОХАХ (простыми словами)
================================================================================

ЭПОХА 1:
  Задача: "Поддерживай связь"
  LLM: "Давай прочитаем угрозу и нагрузку, потом allow_traffic"
  Система читает данные с шумом
  Охранник (verifier): "Стоп! Угроза может быть до 82, а порог 30"
  Результат: safe_fallback (ничего опасного не делаем)

ЭПОХА 2:
  Задача: "Разберись с auth anomalies"
  LLM снова хочет allow_traffic
  Охранник снова блокирует
  Бюджет приватности почти кончился

ЭПОХА 3:
  Задача: "Переоценка после mitigation"
  LLM: "Рекомендую block_traffic" (блокировать — безопасное действие)
  Охранник: "Ок, block всегда разрешён"
  Система блокирует аномальные сессии в данных
  Это closed-loop: решение повлияло на сеть!

6. КАК ВКЛЮЧИТЬ НАСТОЯЩИЙ ChatGPT
================================================================================

1. Зарегистрироваться на platform.openai.com
2. Создать API key
3. copy .env.example .env
4. Вписать OPENAI_API_KEY=sk-...
5. python main.py
6. В выводе будет "LLM provider: gpt-4o-mini" вместо "mock"

Стоит копейки для демо (~0.01$ за запуск).
Без ключа — mock, и это нормально для защиты.

7. ЧТО ГОВОРИТЬ ЕСЛИ СПРОСЯТ
================================================================================

"Почему threat=71, а LLM не знает?"
  -> DP-шум + verifier работают на зашумлённых значениях.
     Raw 71 показывается только в banner main.py для демонстрации
     что LLM действительно не видит правду.

"Это настоящая 6G сеть?"
  -> Нет, симуляция на структурированных данных. Но архитектура
     соответствует статье DP-Guard и готова к интеграции с O-RAN.

"Зачем mock если есть OpenAI?"
  -> Mock для offline/CI/университета. OpenAI для adaptive LLM behavior.

"Что в audit.jsonl?"
  -> Каждая строка = одна эпоха: intent, plan, DP values, decision.
