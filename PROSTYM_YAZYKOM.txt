1. О ЧЁМ ВООБЩЕ ЭТОТ ПРОЕКТ? (одной фразой)
================================================================================

Представь умного помощника (нейросеть / LLM), который управляет безопасностью
сети 5G/6G. Он хочет решать: "пропустить трафик" или "заблокировать".

ПРОБЛЕМА: если дать ему настоящие данные абонентов — это нарушение приватности.
Злоумышленник или ошибка LLM могут "утечь" личную информацию.

РЕШЕНИЕ DP-GUARD:
  - LLM НИКОГДА не видит настоящие цифры
  - Он видит только "размытые" (зашумлённые) цифры
  - Перед каждым действием есть проверка: "а точно ли это безопасно?"
  - Есть лимит: сколько раз можно "подглядывать" в данные

Это как врач, который видит не твой точный пульс 87, а "примерно 85–90",
и ещё у него есть лимит — не больше 3 измерений в день.

2. СЛОВАРЬ — ЧТО ЗНАЧАТ СТРАННЫЕ СЛОВА
================================================================================

LLM (Large Language Model)
  → Большая языковая модель. По сути — "умный текстовый робот".
  → В нашем проекте пока НЕ настоящий ChatGPT, а заглушка (mock_llm.py),
    которая заранее знает, что ответить. Это нормально для прототипа.

Телеметрия (telemetry)
  → Данные о сети: сколько подключений, уровень угрозы, аномалии и т.д.
  → Как "показания датчиков" у сети.

Raw data / сырые данные
  → Настоящие, точные цифры. Например: threat_level = 45.
  → В нашем коде они лежат в RawTelemetryStore и спрятаны.

DP / Differential Privacy / дифференциальная приватность
  → Способ показывать статистику так, что нельзя понять, есть ли в данных
    конкретный человек/устройство.
  → Делается через добавление случайного шума к цифрам.

Шум (noise)
  → Случайное число, которое прибавляют к настоящей цифре.
  → Например: было 45, стало 44.28 или 47.1 — каждый раз чуть по-разному.

Laplace mechanism / механизм Лапласа
  → Конкретный способ добавить шум. Не важно запоминать формулу.
  → Главное: чем больше шума — тем лучше приватность, но хуже точность.

epsilon (ε, "эпсилон") / privacy budget
  → "Стоимость" одного запроса к данным в единицах приватности.
  → Маленький ε = много шума = хорошая приватность, но цифры неточные.
  → Большой ε = мало шума = точнее, но приватность хуже.
  → ε_tot = общий лимит на все запросы (у нас 1.2).

Privacy budget / бюджет приватности
  → Как лимит на карте. Потратил 0.7 — осталось 0.5.
  → Когда лимит кончился — новые запросы к данным запрещены.

Privacy filter / privacy accountant
  → "Кассир", который следит за лимитом.
  → Перед каждым запросом спрашивает: "хватит ли бюджета?"

Orchestrator / оркестратор
  → "Дирижёр" всей системы. Связывает все части в один цикл:
    получил задачу → спросил LLM → прочитал данные → проверил → выполнил.

Plan / план
  → Список метрик, которые LLM хочет узнать, и сколько ε это стоит.

Proposed action / предложенное действие
  → Что LLM советует сделать: allow_traffic, block_traffic и т.д.

Admissibility / допустимость
  → "Можно ли безопасно выполнить это действие?"
  → Даже если LLM сказал "пропусти трафик", verifier может сказать "нет".

Verifier / проверяющий
  → Жёсткий охранник. Не доверяет LLM на слово.
  → Смотрит на зашумлённые цифры и думает: "а в худшем случае?"

Confidence interval (CI) / доверительный интервал
  → Диапазон, где с большой вероятностью лежит настоящее значение.
  → Пример: [35.06, 53.50] — "угроза где-то между 35 и 53".

Safe fallback
  → Безопасное действие по умолчанию, когда всё пошло не так.
  → У нас это safe_fallback = "ничего опасного не делаем".

Epoch / эпоха
  → Один полный цикл: задача → план → чтение данных → проверка → действие.

3. ЧЕТЫРЕ ЧАСТИ СИСТЕМЫ — КТО ЗА ЧТО ОТВЕЧАЕТ
================================================================================

Представь 4 сотрудников в офисе безопасности сети:

┌─────────────────────────────────────────────────────────────────────────┐
│  1. TELEMETRY PLANE (telemetry_plane.py)                                │
│     "Единственный, кто видит настоящие цифры"                           │
│                                                                         │
│     • Хранит raw data в сейфе (__raw_data)                                │
│     • Когда просят метрику — добавляет шум и отдаёт "размытую" цифру    │
│     • Никто другой к сейфу доступа не имеет                             │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│  2. PRIVACY ACCOUNTANT (privacy_accountant.py)                          │
│     "Бухгалтер приватности"                                             │
│                                                                         │
│     • Следит за лимитом ε (бюджетом)                                    │
│     • Перед запросом: "Есть деньги на счету?"                           │
│     • Если нет — кидает ошибку PrivacyBudgetExceededError                │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│  3. ADMISSIBILITY VERIFIER (admissibility_verifier.py)                   │
│     "Охранник на выходе"                                                │
│                                                                         │
│     • LLM сказал: "пропусти трафик"                                     │
│     • Охранник смотрит: а если угроза на самом деле высокая?           │
│     • Считает "худший случай" (верхняя граница интервала)               │
│     • Если опасно — блокирует и включает safe_fallback                  │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│  4. ORCHESTRATOR (orchestrator.py)                                       │
│     "Начальник смены"                                                   │
│                                                                         │
│     • Получает задачу от оператора (intent)                             │
│     • Спрашивает LLM: "что делать?"                                     │
│     • Запускает чтение данных через telemetry + accountant              │
│     • Отдаёт результат verifier'у                                       │
│     • Выполняет действие или fallback                                   │
└─────────────────────────────────────────────────────────────────────────┘

4. ЧТО ПРОИСХОДИТ В main.py — ПО ШАГАМ, КАК В ФИЛЬМЕ
================================================================================

В main.py мы подкладываем "фальшивые" данные сети:
  • threat_level = 45        (угроза ВЫСОКАЯ, порог безопасности = 30)
  • active_connections = 1200
  • anomaly_score = 38

LLM и orchestrator эти 45 НЕ ВИДЯТ. Видят только зашумлённые числа.


--- ЭПОХА 1 ---

1. Оператор говорит: "Поддерживай связь для eMBB slice"
2. Mock LLM отвечает:
   - "Сначала прочитай threat_level (стоит 0.4 ε) и active_connections (0.3 ε)"
   - "Я предлагаю: allow_traffic (пропустить трафик)"
3. Accountant проверяет: 0.4 + 0.3 = 0.7 ≤ 1.2? Да, можно.
4. Telemetry читает данные, добавляет шум:
   - threat_level: z_noisy ≈ 44.28 (настоящее 45 скрыто)
   - connections: z_noisy ≈ 1238.62
5. Accountant списывает 0.7 ε. Осталось 0.5 ε.
6. Verifier смотрит:
   - Для threat_level интервал [35.06, 53.50]
   - Верхняя граница 53.50 > порог 30 → ОПАСНО!
7. Результат: allow_traffic ЗАБЛОКИРОВАН → выполняется safe_fallback

ЧТО СКАЗАТЬ ПРЕПОДАВАТЕЛЮ:
  "LLM предложил пропустить трафик, но система не дала — потому что
   даже с учётом шума угроза может быть выше безопасного порога."


--- ЭПОХА 2 ---

1. Новая задача: "Пересмотри безопасность после алерта"
2. LLM снова хочет allow_traffic, просит ещё метрики (0.3 + 0.2 ε)
3. Accountant: осталось 0.5, нужно 0.5 — можно.
4. Telemetry выдаёт новые зашумлённые значения.
5. Verifier снова блокирует (угроза всё ещё высокая).
6. Бюджет полностью потрачен: 1.20 / 1.20, осталось 0.

ЧТО СКАЗАТЬ:
  "Вторая эпоха показывает, что бюджет приватности конечный —
   после нескольких запросов лимит заканчивается."


--- ЭПОХА 3 ---

1. LLM хочет ещё запросы, но бюджет = 0.
2. Privacy filter сразу отклоняет план.
3. Даже до чтения данных дело не доходит.

ЧТО СКАЗАТЬ:
  "Третья эпоха — privacy filter не пустил, потому что бюджет исчерпан.
   Это защита от бесконечного 'подглядывания' в данные."

5. ЗАЧЕМ ЭТО ВСЁ НУЖНО В 6G (простая аналогия)
================================================================================

6G сети будут управляться почти без людей ("zero-touch").
ИИ будет сам решать: блокировать ли атаку, менять настройки и т.д.

Но:
  ✗ Нельзя показывать ИИ личные данные абонентов
  ✗ Нельзя слепо доверять решениям ИИ
  ✗ Нужен математически доказуемый лимит утечки информации

DP-Guard решает все три проблемы:
  ✓ Данные идут только через "размытие" (DP)
  ✓ Есть лимит запросов (privacy budget)
  ✓ Есть проверка безопасности (verifier)

7. ЧТО ГОВОРИТЬ НА ЗАЩИТЕ / ПОКАЗЕ ПРЕПОДАВАТЕЛЮ (готовый текст)
================================================================================

Можешь прочитать почти дословно:

  "Я реализовал скелет архитектуры DP-Guard из статьи.
   Это система, где LLM-оркестратор управляет безопасностью 6G-сети,
   но не имеет доступа к сырым данным абонентов.

   Архитектура разделена на 4 модуля:
   1) Telemetry Plane — единственный доступ к raw data, добавляет DP-шум
   2) Privacy Accountant — следит за бюджетом приватности
   3) Admissibility Verifier — проверяет безопасность действий LLM
   4) Orchestrator — связывает всё в closed-loop цикл

   В демо main.py используются тестовые данные: уровень угрозы 45
   (выше порога 30). LLM предлагает пропустить трафик, но verifier
   блокирует это решение. После двух эпох бюджет приватности
   исчерпывается, и privacy filter запрещает новые запросы.

   Сейчас это прототип-скелет: LLM заменён заглушкой, нет реального
   API OpenAI. Но ключевые механизмы — Laplace noise, budget tracking
   и admissibility check — работают."

8. ЧАСТЫЕ ВОПРОСЫ (которые могут спросить)
================================================================================

В: Почему LLM не видит число 45?
О: Потому что telemetry_plane добавляет шум. Это главная идея DP — скрыть
   точное значение, но дать полезную статистику.

В: Почему блокируют allow_traffic, если z_noisy=44.28 < 45?
О: Verifier смотрит не на одну цифру, а на интервал "от-до".
   Верхняя граница 53.50 > 30 → в худшем случае опасно → блок.

В: Что такое safe_fallback?
О: "Безопасный режим по умолчанию". Лучше ничего не делать, чем сделать
   что-то опасное.

В: Зачем epsilon, нельзя просто "3 запроса в день"?
О: ε — более точная математическая мера. Разные запросы "стоят" по-разному.
   Один дорогой запрос тратит больше бюджета, чем дешёвый.

В: Это уже готовая система для 6G?
О: Нет, это учебный скелет (v0.1). Показывает идею и работающий цикл.
   Для продакшена нужны тесты, реальный LLM, интеграция с сетью и т.д.
