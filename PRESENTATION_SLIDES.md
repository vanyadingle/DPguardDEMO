## СЛАЙД 2: Проблема и уязвимости автономных сетей 6G
- **Автономия Zero-Touch в 6G:** Управление переходит к автономным агентам на базе LLM.
- **Риск утечки данных (Privacy Leakage):** Сырая сетевая телеметрия содержит персональные данные абонентов (UE ID, сессии, посещенные ресурсы, сбои аутентификации). Прямая передача телеметрии в LLM нарушает приватность и требования регуляторов.
- **Риск галлюцинаций LLM:** Сгенерированные нейросетью действия могут быть семантически некорректными или разрушительными для сети.
- **Ключевой вызов:** Как позволить LLM принимать правильные решения, **запретив ей видеть сырые данные** и математически ограничив утечку приватности?

## СЛАЙД 3: Архитектура DP-Guard (4 плоскости)
1. **Telemetry Plane (Плоскость телеметрии):**
   - Инкапсулирует сырые данные в защищенном контуре `RawTelemetryStore`.
   - Выдает метрики только через механизм Лапласа Lap(Delta1 / eps).
2. **Policy Plane (Плоскость политик):**
   - Ролевой доступ (Pi: Role -> T) и лимиты бюджетов [eps_min, eps_max].
3. **Orchestration Plane (Плоскость оркестрации / LLM):**
   - LLM выступает только как *Proposal Generator* (генератор гипотез), получая обезличенный контекст.
4. **Verification Plane (Плоскость верификации):**
   - Математическая проверка допустимости Adm(a, z) с доверительным интервалом B_beta(z) на уровне надежности 1 - beta = 95%.

## СЛАЙД 5: Доказательство №2 — Механизм Differential Privacy и Privacy Filter
- Механизм чистого eps-DP: M(X) = q(X) + eta, где eta ~ Laplace(Delta1(q) / eps).
- Каталог типизированных метрик со строгой L1-чувствительностью Delta1.
- **Privacy Filter:** Перед каждым чтением проверяет sum(eps_i) <= eps_tot. При попытке перерасхода запрос блокируется.

## СЛАЙД 6: Доказательство №3 — Admissibility Verifier (Защита от ошибок LLM)
- Под шумом истинное значение z неизвестно, но локализовано в доверительном множестве:
  B_beta(z) = [z - t_beta, z + t_beta],  t_beta = (Delta1 / eps) * ln(2 / beta)
- При beta = 0.05 надежность составляет 95%.
- Разрешающие действия (`allow_traffic`) проверяются по **наихудшей верхней границе** угрозы.
- Если верхняя граница превышает порог безопасности (30.0), действие **блокируется** и включается `safe_fallback` (deny-by-default).

- **Эпоха 1:** Угроза в сети высокая (71.0). LLM предлагает разрешить трафик -> **Верификатор блокирует команду** -> Выполнен `safe_fallback`.
- **Эпоха 2:** LLM адаптивно запрашивает метрики сбоев авторизации -> Снова блокировка.
- **Эпоха 3:** LLM понимает ситуацию и генерирует `block_traffic` -> **Верификатор одобряет** -> Аномальные сессии изолированы.
